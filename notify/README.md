# 通知

> 第 #55 轮："你要更新了或者有什么发现，总得提示一下本人。"
> v0.1 现状：**只落账本 + 终端输出**；渠道（GitHub / webhook）属 Issue 0019。

## 1. 三条必须回答的问题

原方案只给了"高/中/低"三档触发条件，没回答真正会出事的三件事：

| 问题 | 回答 |
|---|---|
| 谁判定"值得提示"？ | 规则判定，不是模型自己判定。模型说"我有重大发现"≈ 噪音。规则写在下面表里，可被审。 |
| 重复提示怎么办？ | 同一 `event_id` 24 小时内只发一次；状态变化（如 unresolved → resolved）才再发。 |
| 一直没人回应怎么办？ | 记"未回应数"进仪表盘；**回应率 <50% → 触发通知策略复审**。没人回应的告警等于没告警。 |

## 2. 分级（与 `lab/cli.py` 的 alert 事件对应）

**高（立即，必须人决策）**

- 红线命中（`lab lint` 高危）
- 预算闸门拦截（`run` 返回 3）
- 连续 2 次回滚 → 自动 FROZEN
- 人工冻结（`lab freeze`）
- 账本哈希链断裂（`verify` 失败）

**中（每日汇总）**

- 一次回滚（未冻结）
- 知识条目复审到期
- 新增白名单条目
- PR 待审超过 3 天

**低（每周汇总）**

- 周报生成
- 依赖有更新
- 指标在阈值内波动

## 3. 渠道与降级

| 渠道 | 状态 | 说明 |
|---|---|---|
| 终端 stdout | ✅ 已有 | 每次都打；`lab` 退出码本身就是信号（0/1/2/3） |
| `state/ledger.jsonl` | ✅ 已有 | 审计源，渠道失败也不丢 |
| GitHub Issue `[ALERT]` | ⏳ Issue 0019 | 高优先级开新 Issue |
| webhook / 邮件 | ⏳ Issue 0019 | 失败时降级到终端并记录，**不许静默** |

## 4. 防疲劳

- 中低优先级合并成 digest，不逐条推。
- 24 小时去重；`/snooze` 可静音低优先级 ≤7 天。
- 连续 3 天无高危 → 自动降低中优先级频率。
- 每周统计：发出数 / 回应数 / 平均响应时间；回应率进仪表盘。

## 5. 回应格式

```
/ack <event_id> pause|rollback|freeze|continue
/ack <event_id> note: <备注>
/snooze low 7d
```

`/ack` 会写一条账本事件（`event="ack"`），所以"我回应过了"是可查的，不是记忆。

## 6. 为什么不让模型自己发通知

因为它无法判断"这条值不值得打扰人"。把它做成规则，好处是：误报可以被统计、被调参、
被关掉；坏处是漏报。所以额外加一条**心跳**：如果 7 天没有任何事件，发一条低优先级
"系统仍在运行"——用来区分"没事发生"和"监控坏了"。
