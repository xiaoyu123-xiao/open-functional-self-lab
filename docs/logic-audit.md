## 一、我自己的代码里的 6 个真问题（全部已修，v0.1.4）

### 1. 三个预测器的"单步最优占比"加起来 168% —— 统计口径错误

```
random + persistence + linear = 168.2%
```

原因：判平局用 `step_errors[name] == best`，三者并列时**都算赢**。
修法：并列单独计数（`tie_rate`），只有严格最优才记胜场；报告里直接打印校验行：

```
校验：三者占比 + 并列 68.2% = 100.0%（必须等于 100%）
```

**为什么这个 bug 危险**：它会让"我的预测器 95.7% 的时候最好"这种话听起来极其可信，
而实际上大部分是并列。这类错误在论文里叫"分母偷偷变大"。

### 2. 仪表盘上的预算永远是 0/1000

账本里真实扣费是 `{'kind': 'steps_per_run', 'amount': 1.0, 'run_id': 'run-005'}`，
但 `lab status` 显示 `steps_per_run: 0/1000`——因为 `Budget` 的 `run` 窗口依赖
`run_id`，而仪表盘构造 `Budget` 时不传 `run_id`，于是任何扣费都匹配不上。

修法：`_effective_run_id()` 回落到"账本里最近一次 run"。现在显示 `30.0/1000`。

### 3. 评审是"自己宣布通过"的

原流程 `run` 结束时写的是：

```
REVIEWING → READY，reason="独立评审通过（占位规则）"
```

也就是说：没有任何人评审，程序自己给自己判了通过，然后把状态改回 READY。
这直接违反 `SECURITY.md` 里"主 Agent 不得自评"和 `logic/README.md` 里的状态机语义。

修法：`run` 现在**停在 REVIEWING**；必须显式执行 `python -m lab.cli review --pass`
（或 `--fail --reason "..."`）才回到 READY。未评审就再 `run`，会被拒绝：

```
上一轮还没评审：先 python -m lab.cli review --pass，或 review --fail --reason 原因
```

### 4. "单次上限"被当成"总量上限"，等于没有约束

`steps_per_run = 1000` 只限制**一次 run**。连续 `run` 100 次就是 10 万步，账单一分不多扣。
原来文档里写的"预算硬闸门"在这层上是假的。

修法：新增 `steps_per_day = 5000`（UTC 日窗口），`run` 前同时校验两个闸门，每步同时扣两个账。

### 5. 通知的"回应率"把自己算进分母 —— 越提醒越低

`notify-health` 这条"你的告警可能在失效"的提醒本身是 `needs_action=True`，
于是它会进入回应率的分母：提醒越多 → 回应率越低 → 更容易再提醒。

修法：健康提醒改为 `needs_action=False`，并在统计时显式排除 `kind == "notify-health"`。

### 6. `verify` 只校验 state.json 自洽，不校验它与账本是否一致

`state.json` 和账本是两个写入点（先 state，后 ledger）。中间崩溃、或者有人手改其中一个，
`verify` 都会放行——而"账本是唯一事实来源"是这个项目的核心承诺。

修法：`verify` 增加交叉校验，逐条比对 `state.json` 的转换序列与账本 `transition` 事件序列：

```
[OK] 状态与账本一致：4 次转换一一对应
[FAIL] 状态与账本一致：state.json 3 次转换 vs 账本 4 次（不匹配）
```

## 二、还存在的逻辑缺口（**没有修**，诚实列出）

| # | 缺口 | 为什么没修 | 影响 |
|---|---|---|---|
| 1 | `wall_clock_hours_per_run` 是"步数 × 0.01h"的**估算**，不是真实耗时 | 需要接入真实时钟采样，属 Issue 0014 | 它挡不住"跑很久"，只能挡"跑很多步" |
| 2 | `checkpoint` 只记录账本哈希，**没有真正"恢复到某次 checkpoint"** 的能力 | 回滚演练需要真实权重/数据，属 Issue 0013 | `rollback` 目前是"状态回退"，不是"数据恢复" |
| 3 | `state.json` 先写、账本后写，**中间崩溃仍会不一致** | 修它要做两阶段提交或"只写账本 + 重算状态" | 现在能被 `verify` 发现，但不能自愈 |
| 4 | 没有并发锁：两个 `run` 同时跑会互踩 `state/` | 单机单人场景，属 Issue 0016 | 多开窗口会 corrupt |
| 5 | `ack` 的回应率窗口固定 7 天，不随告警频率自适应 | 参数化需要更多真实使用数据 | 冷启动期可能误报 |
| 6 | 所有渠道都是本地的（终端/账本/文件），**没有推送** | 保持"默认离线"，属 0019 的后半部分 | 你不打开命令行就看不到 |

**这 6 条的共同点**：它们是"设计边界"，不是"我漏了"。写在这里是为了让下一个人
（或者三个月后的我）不用重新发现一遍。
