# 协作

> 第 #52 轮："这是一个双方共同进步、互惠互利的模板。"

但这个"双方"里，有一方不会写记录、不会道歉、也不会记得昨天承诺过什么。
所以协作规则必须假设：**系统是那个会遗忘、会漂移、会自我合理化的一方。**

## 1. 人机分工

| 角色 | 谁 | 做 | 不做 |
|---|---|---|---|
| 发起人 | 人 | 定目标、批高风险改动、写"我学到了什么" | 不写核心代码（避免自己批自己） |
| 执行者 | 人 / Agent | 认领 Issue、写代码、跑实验、贴输出 | 不自评、不改闸门 |
| 评审者 | 独立规则或另一模型 | 只回答"过/不过"，附理由 | 不与执行者同源 |
| 记录者 | 人 | 周报、进步日志、ADR | 不美化失败 |

## 2. 进步日志（每周至少一条）

```markdown
### 2026-11-04
- 人学到了什么：
- 系统改进/退步了什么（附指标）：
- 遇到的问题（失败也要写）：
- 下周计划（对应 issues/ 编号）：
```

判据：如果一条日志里"系统改进了什么"只有形容词没有数字，这条日志不合格。

## 3. ADR（架构决策记录）

`collab/adr/0001-*.md`：

```markdown
# ADR-0001: 为什么状态机要能从任何状态冻结
状态：已接受
背景：原方案只允许 ROLLING_BACK → FROZEN，导致"跑得好好的时候发现异常"冻不住。
决定：除 ARCHIVED 外所有状态都允许 → FROZEN。
后果：+ kill switch 随时可用；− 多一条需要测试的转换（已在 tests 覆盖）。
批准：发起人，2026-11-04
```

什么时候必须写 ADR：改了状态机、改了预算口径、加了依赖、改了红线条目。
不写 ADR 的 PR 会被维护者退回——不是因为流程主义，而是半年后没人记得为什么这么改。

## 4. 30 分钟入门

1. 读 `README.md` 的"这是什么/这不是什么"（5 分钟）
2. `python -m lab.cli doctor && python -m lab.cli run --steps 20 && python -m lab.cli viz`（5 分钟）
3. 打开 `viz/status.md`，看懂四个区块（5 分钟）
4. 在 `issues/README.md` 挑一个 ⏳，按模板写认领留言：硬件 / 时间 / 安全承诺（5 分钟）
5. 提第一个 PR：改文档错别字也算（10 分钟）

## 5. 常见误解

| 误解 | 实际 |
|---|---|
| "我先自己跑通再接别人" | 先提 PR 再完善，评审是为了让**你**少走弯路 |
| "失败了不好发" | 失败记录是交付物，`docs/failure` 相关条目比成功更被需要 |
| "看不懂代码就只能等" | 记录者/评审者/发起人都不需要写代码 |
| "没有 GPU 就没法参与" | v0.1 全部任务除 0013 都是纯 CPU |
